# 大厂真实体验研究：让局域网里的“一起”自然发生

研究日期：2026-11-03。范围是公开官方文档所描述的交互与设计原则；这不是对 Apple、Nintendo、PlayStation 或 Discord 实际设备的亲自操作记录，也不是用户测试结论。下文的“来源观察”是官方材料的陈述；“项目推论”是根据本产品约束提出的假设，需要原型和真实用户验证。具体平台版本、地区、会员资格会影响产品行为。

## 项目基线与约束

当前产品是三人以内局域网房间：自动发现、创建和地址加房间码手动加入；任何成员可取得唯一共享席位；本机麦克风、观看/只语音、接收端音量可独立操作。画面和系统音频通过浏览器采集，权限、选屏、音频可用性与自动播放由浏览器决定；共享系统音频的隔离不确定，不能声称没有回声。当前本机主播选择“只聊语音”会先停止自己的共享；用户主动选择只语音后，不能因房间更新自动切回观看。现有自动发现每三秒刷新；若要让列表更稳定，应避免刷新时破坏正在操作的卡片与焦点。房间/麦克风/采集/系统音频/观看应分别表述，不能用单一“已连接”代替。

## 证据卡：具体事实、可迁移行为与边界

### 1. 首次相遇：先让人走进来，再解释

**来源观察。** [Apple HIG：Onboarding](https://developer.apple.com/design/human-interface-guidelines/onboarding) 主张让人通过使用理解产品，将非必要设置推迟，以就地且与当前任务相关的提示代替一大段教程；[Privacy](https://developer.apple.com/design/human-interface-guidelines/privacy/) 建议在用户实际使用相关功能时才请求权限，并说明用途。[AirDrop 接收说明](https://support.apple.com/en-gb/119857) 则提供有期限的公开接收状态，之后自动退回较严格状态；该具体规则属于 Apple 的生态与版本，不是局域网房间规则。

**项目推论。** 首页把“附近房间 / 创建房间 / 手动加入”作为三条可执行路径；空列表同时给出创建入口、正在搜索状态与手动加入，不把“没找到”和“发现不可用”合并。加入时说清“麦克风稍后由你开启”；首次点击麦克风或共享才触发对应浏览器请求。创建时用普通语言说明“同一局域网的人可发现”，并保留可修改的公开开关；不要承诺目前不存在的十分钟自动过期。主路径可通过不阻塞的就地提示解释，诊断只在需要时展开。

**不能照搬。** AirDrop 的联系人、账号与系统级临时可见性机制不等于本项目的局域网发现；浏览器选屏和麦克风授权样式不可由网页控制。切勿仿造系统权限弹窗或宣称系统自动保护了所有隐私。

### 2. 一起待着：语音房间本身就是目的

**来源观察。** [Nintendo GameChat FAQ](https://en-americas-support.nintendo.com/app/answers/detail/a_id/68390) 把不同游戏或什么也不玩时的共同相处纳入场景；可以单独调整其他用户音量，按个人需要改变布局。它依赖 Switch 2、网络与相应会员等条件。[Discord Go Live](https://support.discord.com/hc/en-us/articles/360040816151-Go-Live-and-Screen-Share) 允许人进入语音频道聊天而不观看直播，并能单独调整直播音量。[Apple SharePlay 的电话说明](https://support.apple.com/en-sg/guide/iphone/iph316a8f125/ios) 区分所有人共享的播放动作与各人单独控制的音量/字幕。

**项目推论。** “三个人已在一起”应该是稳定的主场景，即使没有画面也不是失败或空播放器。成员位显示真实存在、角色与连接状态；本机/远端、麦克风/共享声音分开，音量滑杆明确标明“只影响我听到的”。展示“有人在分享 · 观看”但让用户保留只聊语音的选择；正在说话、音量动态或观看人数只有在确有可靠数据时才出现。

**不能照搬。** 本项目没有 Nintendo 的专用硬件降噪、摄像头或字幕能力，也没有 SharePlay 的共享播放时间线；不能把音量调节写成影响其他人。不能因为他人开始共享就强行改变用户此前主动选择的只语音状态。

### 3. 共享接力：提出意图与真正交接是两件事

**来源观察。** [FaceTime 屏幕共享](https://support.apple.com/en-au/guide/iphone/iph327b4b53c/27/ios/27) 支持自己开始或请对方分享，开始前有倒计时并可停止；[PlayStation Share Screen](https://www.playstation.com/en-gb/support/games/ps5-share-screen/) 在语音小队内可开始共享、通知参与者，也可向一位玩家发起分享请求；[FaceTime Mac](https://support.apple.com/en-ie/guide/facetime/fctmdcf2007a/mac) 文档描述更换共享的窗口/应用。它们的对象和交接机制各不相同，不能推断任何一款自动实现本项目所需的主播转移。

**项目推论。** 有人共享时，在当前分享者附近明确“正在分享 · 等对方停止后可分享”；空闲时给“分享我的屏幕”；分享者有明确的“停止分享”，停止后语音继续。可在未来探索“请对方分享”或“轮到我”的意图，但它必须是有明确送达/取消/拒绝状态的新消息协议，而不是假按钮或自动抢占。对选屏后未拿到系统声音的现有待选择状态，展示“画面还未共享”“继续仅画面”与“取消”，并以真实采集结果驱动。

**不能照搬。** FaceTime 的同一分享者替换窗口不等于多人之间原子转移分享权。本项目浏览器的 `getDisplayMedia` 必须跟随用户手势、并由系统选屏；网页不能代替用户替对方开始，也不应在别人占用时后台预采集。倒计时可能暗示可以撤销已开始的系统采集，除非实现真实可取消时序，否则不应加。

### 4. 可发现与有边界的控制

**来源观察。** [Nintendo C 按钮说明](https://www.nintendo.com/en-gb/Support/Nintendo-Switch-2/General-Tips-for-Using-Nintendo-Switch-2-2843789.html) 描述固定入口，在会话中控制麦克风和共享；[FaceTime 安全说明](https://support.apple.com/en-ca/guide/personal-safety/ips48fe06838/web) 说明如何识别当前屏幕共享及如何停止。[Discord 文档](https://support.discord.com/hc/en-us/articles/360040816151-Go-Live-and-Screen-Share) 描述分享者标识和观看入口。Apple HIG 的[设计原则](https://developer.apple.com/design/human-interface-guidelines/design-principles) 强调可用状态、变化反馈及一致性。

**项目推论。** 桌面页面有稳定的“房间操作带”：麦克风状态、谁在分享/停止、观看或只语音、声音入口；主要控件兼有文字、键盘焦点及状态语义。观看时画面优先，控制带可因空间而收纳，但焦点进入时必须可见。清楚区分“正在向朋友发送系统声音”“我正在听系统声音”“当前没有捕获系统声音”。窗口外的系统共享标识依赖浏览器，产品内仍需明确可见的停止入口。

**不能照搬。** 游戏主机有全局物理 C/PS 按键与系统悬浮层；网页不保证游戏全屏时控制面板或浏览器处于前台。图标只用来辅助文字，不假装本项目拥有系统级常驻控制。

### 5. 等待与感知性能：先有可用动作，再报告真实进度

**来源观察。** [Apple HIG Loading](https://developer.apple.com/design/human-interface-guidelines/loading) 建议尽快显示内容、在等待时允许其他操作；[Progress indicators](https://developer.apple.com/design/human-interface-guidelines/progress-indicators) 区分时长已知和未知的过程，卡住时说明问题及可做的事，不应给误导性百分比。[Alerts](https://developer.apple.com/design/human-interface-guidelines/alerts) 倾向将非紧急信息放在上下文里，模态警告应提供可执行动作。

**项目推论。** 搜索时保留创建和手动加入；连接时显示真实阶段，例如“已加入房间，正在连接画面”，在同一位置逐步更新；允许取消的阶段提供真实取消，未知时长使用不定进度，不做伪造 90%。断线或画面结束时清掉旧帧并说明“语音仍在/正在重连/已断开”，以当前状态为准；不要把诊断原文当主消息。发现空、发现不可用、连接中、加入失败分别有可行的下一步。后台的房间刷新应保留焦点和稳定顺序，而不是让用户点击中的目标突然消失。

**不能照搬。** 官方建议本身不能证明网页连接速度快；显示已连接前必须等真实信令/媒体事件。不可把陈旧画面当实时视频，也不可编造所剩秒数、成员在线或恢复进度。

### 6. 失误恢复与渐进披露

**来源观察。** [Apple HIG 设计原则](https://developer.apple.com/design/human-interface-guidelines/design-principles) 提倡让人能预测并恢复失误；[Alerts](https://developer.apple.com/design/human-interface-guidelines/alerts) 主张仅在必要时中断，并用清楚的动作名；[Nintendo GameChat 设置](https://en-americas-support.nintendo.com/app/answers/detail/a_id/68393/c/950) 把更细的屏幕共享、语音辅助等选项放在会话设置中。

**项目推论。** 常用的开启/关闭麦克风、开始/停止共享、观看/只语音在主操作区；质量、各来源音量、系统声音隔离、诊断收在有明确标题的面板。浏览器拒绝麦克风时留在房间，提供重试，并说明仍可接收；选择共享时无系统音频，让用户明确继续仅画面或取消。用户选择只语音将停止本机共享这一后果须在操作附近说明；不要虚构一个可无损撤销的“恢复共享”，重新共享需要再次选屏。失败的离开请求要说明未获确认，同时回到可操作的房间发现页；失败的结束房间不能假称服务器已结束，需保留重试或真实状态。

**不能照搬。** 隐藏高级信息不等于隐藏重要状态：系统声音是否发送、隔离未确认、浏览器阻止播放须在相关操作附近可发现。对已实际停止的屏幕采集，“撤销”不能绕过浏览器再次授权。

## 对现有 Portal / Orbit / Edge 的本质局限

- **Portal** 把发现塑造成漂亮的房间对象，但核心仍是“选择一张卡”。在只有零或一间房时大块空白并不自动创造关系感；列表的自动刷新、自己的房间、满员、失败及手动路径才决定信任。演示静态数据也不能证明搜索、焦点与网络故障体验。
- **Orbit** 让三人可见，但三张固定头像仍是成员静态陈列；它没有天然解决声音实际来源、谁可共享、进入和断线过程。过多空位或居中构图会挤压真实操作，特别是窄窗。
- **Edge** 提升画面比重，但当主内容占满视窗，成员、语音状态、停止分享、恢复观看和异常反馈容易消失。沉浸与控制不是简单切换显示/隐藏；全屏、键盘、用户主动只语音及浏览器焦点都需要具体定义。
- **三者直接按阶段拼接** 的共同风险是以三个页面外观替代一个连续关系：成员、分享权、连接状态和选择随阶段跳转，用户须反复重新定位。下一轮应将连续性、角色视角与失败恢复作为结构本身来设计，而非最后补丁。

## 三种结构上不同的新概念（均为待验证假设）

### A.「一张会生长的房间票」：房间对象连续展开

**结构。** 首页房间票就是入房后的同一个对象：票面从“朋友的房间 · 2/3 · 正在分享”扩展为成员与当前活动；共享出现时票面内生长出画面区域，不跳到另一套页面。顶部稳定显示房名与连接信息，底部固定同一组动作；只有核心内容区扩展。

**关键旅程。** 空列表给创建和手动加入；点房间立即显示“正在加入”并锁定该票，不把网络耗时伪装为成功；加入后票内显示三名实际成员。对方分享时出现真实分享状态和观看入口；本机只语音则保留票面和语音。共享结束回到成员状态，不保留冻结帧。

**潜在惊喜。** “我从一个房间门牌走进了同一个房间”可能让变化更好理解；信息空间由实际活动生长，形成连续感。

**代价与待验证。** 卡片到画面变形在窄窗和 reduced-motion 下要有直接切换；发现轮询不可替换用户焦点。验证参与者是否知道自己真的已入房，以及焦点/取消是否可靠。现有能力可原型；平滑共享接力仍需协议，不能伪装成已有功能。

### B.「始终在场的声音台」：人是主结构，画面是可加入的活动

**结构。** 房间始终是三个人与一个固定操作台，画面作为房间中可打开或收起的活动层；听语音和看画面是彼此独立的维度，而非不同页面。无共享时不占用巨型空播放器；正在看时画面占主空间，成员压缩为可展开的真实状态条。

**关键旅程。** 已入房后先看到“我 / 房主 / 另一成员”的实际状态，主操作在同一位置；他人共享时其成员位旁显示真实状态和“观看”，用户可选择加入观看。声音控制按成员和共享声音分组，清楚说明本机调节；离开观看不会离开语音。主播若选择只语音，事先说明现有实现会停止其共享。

**潜在惊喜。** 从“建立一场直播”转为“我已经和朋友在一起，随时可以看”，也许能降低等人和换活动时的空场感。

**代价与待验证。** 一直显示成员可能侵占游戏画面；需要评估 390px、放大字体及全屏时最低可见控件。不能显示假的声波或在线人数；若未来要看真实音量需明确采样与隐私成本。房间连接与观看实际状态以现有数据为准。

### C.「接力轨道」：围绕当前活动与下一步交接

**结构。** 主界面是一条短轨道：“房间已就绪 → 某人正在分享 → 分享结束”，轨道只显示已发生和当前能执行的动作；成员席位与音频控制在同一侧栏/底部抽屉。画面有时占满主区域，有时轨道显示可执行的“我来分享”；信息组织按事件与权限，不按三个固定页面。

**关键旅程。** 入房显示已在房间；他人正在分享时轨道说明“由谁分享”，观看入口与声音操作紧邻。占用时分享按钮说明需要对方先停止。实际收到停止事件后，同一位置变为“可以分享我的屏幕”；点击后直接进入系统选屏，真实采集成功才显示“正在分享”。失败或取消保留房间和语音并显示下一步。

**潜在惊喜。** 让两个人之间最易尴尬的“谁来、什么时候可以开始”变成可理解的连续事件；不需要读技术状态才能知道下一步。

**代价与待验证。** 轨道若无限堆叠会变成日志；只保留当前事件和可执行下一步。向对方请求分享、排队和主动交棒都需要新的信令、超时与取消语义；第一版必须明确没有这些动作。验证首次使用者能否区分“等待对方停止”与“我可开始”，以及是否误以为系统会自动交棒。

## 建议的比较与验收问题

先用同一套真实状态数据做三种低保真可交互原型，而不是先确定配色或动效。每人单独完成：发现一间房并加入、在无人共享时聊天、以接收者选择只语音再恢复、遇到他人占用时理解谁能分享、拒绝麦克风仍继续、系统声音缺失时做选择、断线后判断是否还在房间。观察无需讲解的成功率、首次找到主动作的时间、错误判断与可恢复性，而不只询问“喜欢哪个”。

验收需覆盖 1440×900、900px 与 390px，键盘焦点、200% 缩放、长房名、减少动态效果、直播全屏；并使用实际浏览器与设备验证媒体、自动播放、音量、停止采集和隔离状态。官方文档支撑的是设计方向，不能代替用户可用性、真实声画质量或发布满意度的证据。
