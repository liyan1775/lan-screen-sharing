# 交叉评审：让房间真正帮助朋友一起看

评审对象：[大厂研究](big-tech.md)、[前端技能研究](frontend-skills.md)、[人类专家研究](human-experts.md)，以及实际查看的 [语音基线截图](baseline-voice.jpg)。截图只展示房主单人在房间、两席空位的一个静态状态；不能据此判断真实连接、动态画面、交接或设备表现。

## 看见的基线与关键问题

截图的文案“一起聊，随时分享”方向正确：房间本身就可以是目的。实际视觉上，标题、三张同尺寸成员卡、另一整条操作栏和三个折叠设置区依次堆叠。两个空位占了成员区域大部分面积；麦克风、启用声音、只聊语音、选择显示器、停止共享并列，用户要自行判断哪些属于“我能说”、哪些属于“我能听”、哪些影响所有人的共享。画面解释“任何成员都能共享”，但帮助用户完成当下那一步的上下文不在对应对象旁。这是截图中的结构观察，不是声称按钮行为有缺陷。

所谓“聪明”，应是系统利用**已确知的状态**在关键节点缩短判断：朋友在、分享被占用、我已选择只语音、对方停播、当前选屏取消时，给出准确且能执行的下一步，保留人的选择。它不能依赖虚假的声波、预设倒计时、装饰性动画、编造进度或不存在的交接协议。

## 交叉批评：哪些仍可能只是换词

| 方案与来源 | 确有价值 | 仍可能只是旧方案换词的问题 |
| --- | --- | --- |
| 大厂 A 房间票；技能 A 展开房间 | 房间身份连续，发现到入房可避免迷路 | 如果仍是门牌变大、头像排一排、按钮原样搬入，就是 Portal 的动画版本；入房首次成功和停播后接力并未因此更容易。动效关闭也必须有相同理解度。 |
| 大厂 B 声音台；人类 B 共同舞台 | 尊重无画面也能待在一起，观看是个人选择 | 固定三人位加一个画面很容易退回 Orbit；如果“谁听什么/谁能做什么”仍要从分散按钮推理，头像构图不会带来陪伴。安静不应被解释成没人。 |
| 大厂 C 接力轨道；人类 C 接力台 | 明确当前占用和停止后的可用动作 | 如果仅添加“进行中→已结束”时间线而原操作不变，就是旧状态栏换造型；轨道甚至可能成为额外阅读负担。不能让人以为有请求、排队或自动交棒。 |
| 人类 A 共同旅程 | 显示加入与媒体不同阶段，首次引导有价值 | 若每次都按步骤走一遍，就是把设置面板改成向导；熟人只是进来聊聊天，不应被强制进入共享或新手流程。 |
| 技能 B 边缘控制 | 保护画面并考虑键盘、触摸 | 本质与 Edge 很近；藏起面板并不能解决独立收听、停播与接力；只适合承担观看状态的呈现方式。 |

这些材料对真实状态、渐进披露和保护内容的共识可靠，但都还没有证据表明新构图本身会制造惊喜。应保留其原则，原型须在行为上证明优势。

## 主推：在一起的房间 + 情境接力

**产品核心：** 房间持续存在，语音和个人选择可独立；共享画面是房间内随时出现或结束的共同活动。关键不是再做一种页面形状，而是在四个真实状态下就地改变下一步：

1. **独自等待：** 看见“你已在房间，等待朋友”，并在空位附近提供现有可用的邀请/手动加入信息入口；可先检查自己的麦克风、创建共享或安静等待。没有朋友时不伪造在场。房间已创建与语音已连接分别表达。
2. **朋友在场，无共享：** 用紧凑真实成员状态表达“我们在一起”；同一个活动区域明确“还没有人在共享 / 分享我的屏幕”。本机麦克风、我听到的成员与共享音量彼此区分，详细调节按需展开；无需发言即可安静相处。
3. **A 正在共享：** 画面主导观看视图；旁边明确 A 正在分享。每人独立选择观看或只聊语音，并能单独调整自己听到的声音；已主动选择只语音的人不因新共享被自动切回。分享占用时说明“等 A 停止后可分享”，不出现伪请求或排队。主播自己选择只语音若会停止自己的共享，在动作附近提前说明。
4. **A 停止或 B 选屏取消：** 收到真实停播事件后清掉旧帧，活动区域原地说明“分享已结束；房间和语音仍在”（以实际状态为准），并给 B 一个“分享我的屏幕”动作。B 点后交由浏览器选择；取消或失败保留房间与原选择，给出再次选择，真实采集和发送成功后才显示正在共享。不得自动抢占、后台预采集或暗示自动交棒。

**为何值得体验：** 第一次成功由用户看到真实的“朋友已在房间”、理解自己能说能听和能选择看什么构成；最关键的时刻是 A 停播之后，B 不需要先找到设置或猜测是否轮到自己。体验价值来自减少一次社交询问和状态猜测，而不是视觉仪式。个人观看选择不代表其他人也停止观看；本机音量调整只影响自己。

**最大失败风险：** “共同房间”最后仍成为三卡一栏；或者为了显得连贯而夸大真实连接状态，遗漏浏览器授权、系统音频缺失、只语音与主播的特殊后果。重点动作也可能在观看时被隐藏。设计应按本地已实现的状态建模，未知就说未知。

**怎样用原型证伪：** 先做一个可点击的同尺寸原型与现有基线对照，用相同三人状态和文案数据；让未参与设计的人不看说明完成“入房安静等待→选择只语音→A 开播但保持只语音→主动观看→A 停播→自己开始并取消选屏”。记录错误推断、提示次数、动作次数、是否知道自己听到什么，尤其停播至找到下一步的过程。如果仍需解释状态或 B 找不到开始动作，或控制画面遮挡更严重，就否定该结构并修改；可先由项目用户实际体验和启发式走查迭代，不需等招募研究组。原型模拟仅证明交互理解，不证明真实媒体连接。

## 挑战者：活动接力优先

**结构与行为：** 无画面时主区域只展示当前活动及下一步；有分享时画面占据主区域，状态条围绕分享者和真实占用状态。停播后同一位置立刻换为“分享我的屏幕”，而成员与声音以固定、可展开入口保留。与主推相比，它更聚焦反复轮流展示，不以成员关系作为常驻视觉核心；观看/只语音仍属于每个人的明确选择。

**为何值得体验：** 对经常说“我来给你看”的朋友，操作空间围绕当前活动变化，交接路径可能更短，动态内容获得更多空间。

**最大失败风险：** 失去持续陪伴感：无画面时像等待播放器，有画面时朋友消失；频繁的活动状态变化也可能使声音入口难找。它还可能沦为 Edge 加一行状态，未带来行为改善。

**怎样用原型证伪：** 同样状态和任务下，让人静默相处一段时间，然后让 A→B 完成轮流分享；结束后询问是否知道谁仍在、怎样只调整自己的听感、能否不看画面继续聊天。若参与者需要找人、误以为停播等于离房或不如主推顺畅，则淘汰挑战者；若陪伴感无损且交接更容易，则保留用于进一步迭代。不要把用户对某个颜色的喜好当成结构胜出。

## 立即可做的验收顺序

1. 用当前截图作参照，把四个状态和主播/观看者视角绘成同数据的两套交互原型，核对实际可用事件、限制和文案；先对空房、只语音、共享占用、停播和取消逐项做启发式走查。
2. 在浏览器实际视口比较主推、挑战者与基线，检查长房名、窄窗、200% 缩放、键盘、焦点、明暗变化及停止/静音的发现性。按用户实际体验及时修改，再重新验证受影响路径。
3. 有真实设备时再核对浏览器权限、播放策略、系统声音、语音独立性、三人连接与停播；把模拟和真实结果分开记录。任何阶段都不把“未来可请求/排队”写成现有行为。
