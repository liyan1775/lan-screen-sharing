# 交叉评审：把“关系可操作”变成结构，而不是给面板换名字

日期：2026-11-03。范围：`frontend-skills.md`、`human-experts.md`、`big-tech.md`，以及提供的 `baseline-voice.jpg` 和当前生产媒体实现的静态阅读。以下是设计评审与可检验假设，不是用户研究、真实多机媒体或完整无障碍验收。

## 先指出基线真正的问题

截图呈现的是一次**已创建但只有房主**的语音房间：一个大标题、一个包裹三个等权席位的面板、另一条按钮面板，下面再叠邀请与设置折叠项。画面中最大的可视对象是两个等待加入的空位，而“如何请朋友进来”却藏在“备用：手动加入信息”里；音频操作与人分离，用户需要从成员身份跳到独立的声音面板去匹配。截图本身不证明用户找不到操作或共享画面表现如何，但它支持“房间被拆成独立管理模块”这一观察。现有后续源码已有收紧成员样式的修改，因此这张图是候选基线截图，不代表最新源码已重新验收。

主要问题不是配色、是否有头像或有没有卡片，而是**一个用户要在心里完成对象关联**：正在看谁的画面？谁的声音太大？我能否不看画面继续陪着？我能否只调游戏声音？一个真正不同的结构，必须改变这几件事的操作路径或状态保持，而不是把同一组面板安排在新位置。

## 严格评审三份研究

| 研究与方向 | 结构上实际改变了什么 | 未被证明、或仍是旧方案的部分 | 评审结论 |
| --- | --- | --- | --- |
| 前端技能 A「房间展开」 | 如果房间票在加入、失败和观看中保持**同一对象及可返回上下文**，可以减少用户重新定位房间；但这要求真实状态、焦点和对象身份持续。 | 描述大部分仍是门牌扩成成员、再变大画面：它可完全等价于 Portal + Orbit + Edge，尤其当动画结束后仍是成员面板和底部工具栏。视觉连续不等于任务路径更短。 | **有条件的结构变化**。必须演示取消/失败后在原房间直接重试、焦点未丢，不能用展开动效作为成功证据。 |
| 前端技能 B「边缘控制」 | 明确围绕画面保留操作且探索键盘/触控唤出，改变控件发现机制。 | 主要是在 Edge 周围收纳按钮，没有回答“谁的声音、什么来源、离开观看是否离开人”。缩进抽屉甚至可能加一步。 | **观看布局方案，不是新的完整交互模式**。适合作为组件对照。 |
| 人类专家 A「共同旅程」 | 将状态和下一步放在同一处，若真实错误直接在原处恢复，可减少跨面板找操作。 | “每阶段一个主动作”容易把同时聊天、观看、分享等并行行为强行排队；一条阶段时间线不等于人之间关系。 | **可能改变首次路径，未说明熟手并行操作**。应测第二次进入和主动只语音，不仅测首次顺序。 |
| 人类专家 B「共同舞台」 | 若观看开合时成员上下文和每人的声音对象原地保留，能减少场景切换。 | “大舞台 + 旁边的人”与 Edge + Orbit 极近；没有成员对象直接操作时仍是布局。音量状态不必然随“同一舞台”保持。 | **目前主要是布局描述**。必须补充人、声音、画面彼此可操作的关系。 |
| 人类专家 C「接力台」 | 当真实分享结束后，在同一位置把“等待某人停止”变为“我来分享”，让接力下一步可见；这比 disabled 按钮确有路径变化。 | 候选 A/B/C 若以聊天轨迹、队列或“请求交棒”呈现，就超出现有协议；单次观看时完整轨道会成为新面板。 | **改变事件到下一步的路径，但不是自动接力**。第一版只显示已知事实和本机可执行动作。 |
| 大厂研究 A「生长房间票」（本人的方案） | 同上：保留房间身份与失败后的原处操作，有可能减少重新导航。 | 我把连续对象的价值与视觉生长混在了一起；若不支持原处重试和焦点保留，就是 Portal 换皮。 | **不主推**，除非上述行为可实测。 |
| 大厂研究 B「声音台」（本人的方案） | 提出观看是独立选择，成员/声音与画面可同时存在。 | 方案没有具体说明怎样从一个人的画面直达那个人的声音，仍可简化为三头像 + 工具栏；承诺音量保持也忽略轨道结束后音频节点重建。 | **方向可取但原案不够具体**，需要一个可操作的关系模型。 |
| 大厂研究 C「接力轨道」（本人的方案） | 将空闲与占用的同一位置转成下一步，减少用户寻找分享入口。 | 与人类专家接力台高度重合；若只显示当前事件，它还是状态条。没有真实请求/排队协议就不能称为交棒功能。 | **局部行为值得吸收，不足以单独成为完整概念**。 |

三份报告对真实性和恢复边界讨论扎实，但“连接 / 成员 / 画面怎样真实绑定操作”仍停留在原则。独立引用来源不能证明某个方案优于现有界面；`frontend-skills.md` 对旧结构的警惕，与其自己提出的 A、B 存在落差。

## 主推概念：「同伴通道」——先选择关系，再操作那条关系

**核心规则。** 房间中的每个真实同伴是一个可聚焦、可打开的**关系对象**；它代表“我与这个人当前有哪些实际可用的媒体来源”，而不是带一个头像的成员卡。当前分享画面是该分享者对象的一部分：画面边上的分享者名字即同一个关系对象的入口。打开它，直接出现该人的**语音**以及若其确实为当前分享者且存在接收源时的**共享声音**，两者独立静音/调节；每项旁边明确“只影响我听到的”。本机对象则管理本机麦克风，并明确是否自己正在共享，不显示会让人误解为自我收听的远端滑杆。

这不是“成员区再加一个按钮”：**画面、声音和人的对应关系成为同一个可操作对象**。房间工具只处理房间级动作（离开、邀请）；该对象处理成员级/来源级动作；观看状态是用户对当前分享者内容的本机选择。画面主区域可扩张，但关掉画面不会把人和声音从交互结构中拿掉。

### 一次可感知的聪明闭环：游戏太吵，但还想陪朋友聊天

1. 观众 A 正在看 B 共享画面，界面在画面边明确标出“B 正在分享”，该名字与房间里的 B 是同一个可操作入口。
2. A 点击或键盘打开 B：弹出就近控制，显示真实存在的“B 的语音”和“B 的共享声音”。A 调低共享声音，不改变 B 的语音，也不改变其他成员的声音。若共享声音不存在或尚未到达，明确显示不可用，不摆一个无效滑杆。
3. A 暂时不想看画面，选“只聊语音”。画面退出、共享声音在本机暂停、B 的语音及房间保留；同一个 B 对象仍可找到，并提示“B 正在分享 · 恢复观看”。不使用“离开”描述这个动作。
4. A 选择恢复观看，画面回到当前真实分享来源；在**同一音频元素仍存活**时，以现有用户设置继续，且原本用户静音不得被强制解除。若 B 停止/更换共享或轨道结束，显示已结束/不可用，不恢复过期画面；轨道重建后是否记住音量另需实现和测试，不能承诺。

这个闭环的价值是：从画面上的人直接找到对应声源，再退出观看而不丢失共同空间；动作结果都能回到同一关系对象中核对。不需要夸张动效、倒计时、伪说话波纹或自动猜测用户意图。也不保证首次使用者必然觉得聪明——必须靠对照任务验证。

### 本机主播的不同路径

当前实现中，本机有 `screenVideoTrack` 或待处理采集时点击“只聊语音”会先调用 `setScreenStream(null)`：这会结束或取消自己的共享。不能把观众的“只退出观看”文案用于主播；主播操作必须明确为“停止我的共享并只聊语音”，在动作附近提示后果；之后恢复共享需本人重新触发浏览器选屏。也不能自动从一个主播转给另一个人；现有分享权由房间真实状态决定，别人占用时只说明原因，等待释放后让本机用户自主开始。

## 与现有实现的能力边界

| 行为 | 现有证据及能否支持 | 原型/产品必须处理 |
| --- | --- | --- |
| 观众只语音与恢复 | `app.js` 的 `voice-only` 调 `media.setVoiceOnly`；`media.js` 分别控制远端视频轨道和 `systemAudio` 元素，麦克风语音保持；`updatePresentation` 依据当前 presenter 和视图状态绑定画面。**可在既有协议上支持**。 | 不能承诺停止接收网络流量；明确实际音轨不可用、自动播放被拒绝和共享结束；在重连/新房间中核验状态，不自动覆盖用户主动选择。 |
| 在成员对象旁调音 | 音频以 `peerId:role` 映射，`setAudioControl` 分别设置本机 `muted`/`volume`；`onAudioSource` 只在真实音轨出现时通知。**需要重组界面，不需要新信令**。 | 以 peerId 关联，名字只是标签；在音轨到达之前、结束及成员离开时处理可用性、焦点和滑杆销毁。禁止把自己列为远端来源。 |
| 同一个音频节点上保留调节 | `setVoiceOnly` 对共享声音叠加静音条件，`userMuted` 留在音频元素上；元素未销毁时音量也在该元素上。 | 轨道 `ended` 后 `attachAudio` 会移除音频元素，重新创建默认为初始值；跨轨道、重连或换主播长期保留需新增状态映射与测试。 |
| 声音活动提示 | 现有 UI 没有可靠的成员声活动事件；媒体统计不是说话/听见的证明。 | MVP 不显示活动；若之后引入本地分析器，需明确权限、阈值、性能、消失时序及误报，并标为信号活动而非“人在说话/听见”。 |
| 请求接力/排队 | 现有状态可知道 presenter 与占用，但未见用户意图请求、排队、拒绝或送达协议。 | 不展示可点击的假请求、自动接力、队列或发送通知；只在真实释放后允许用户点击现有分享入口。 |
| 跨全屏和窄窗 | `.screen-stage` 是既有全屏根，视频和全屏/指针处理已绑定；普通页面浮层不自动进入该全屏树。 | 把必需控制放在可见全屏上下文或显式退出全屏，验证焦点、Escape、触摸和遮挡；不重建 video 或依赖 hover。 |

## 原型最低场景与否决标准

同一套真实或清楚标注的模拟状态，至少展示：①房间无他人、②三人在场未共享、③B 分享且含系统音频、④B 分享但音频不存在、⑤观众只语音、⑥B 停止、⑦B 断线/音轨结束、⑧本机是主播。测试同时覆盖 390px、键盘、放大和全屏；原型不能把模拟声画、活动、网络或协议标成真实。邀请入口在等待朋友时应可直接发现，而非藏于诊断语境。

对照当前综合预设，给参与者同一个任务：“B 的游戏太吵但我想继续听 B；稍后只聊天，再回来观看。”记录首次找到对应声音的路径、误调他人语音的次数、能否解释只语音后仍在房间、恢复后用户静音是否保留，以及是否独立完成；操作者视角和主播视角分开。若成员对象无法让人找到来源、使关键操作增加步骤、焦点在状态变化时丢失，或无法清楚解释主播停止共享的后果，就否决或重做这个概念。一次成功动画或设计师偏好不足以判优。
