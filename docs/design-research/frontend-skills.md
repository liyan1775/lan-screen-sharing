# 前端设计技能与实现方法研究

调研日期：2026-11-03。范围是当前局域网屏幕共享的正式界面和独立实验室。本文记录可迁移的方法与设计假设；引用的指南是作者的建议，不是本项目完成用户验证的证据。没有安装或执行外部技能脚本，也没有为本次研究启动产品。

## 实际查阅的技能与来源

- Anthropic 原作者的 [frontend-design SKILL.md](https://github.com/anthropics/skills/blob/main/skills/frontend-design/SKILL.md)：先明确产品、受众和主要任务，再定视觉方向、结构和文案；用一次有意义的表达建立识别度，构建后对照场景自评。它明确把奶油底加陶土色、等权圆角卡片、装饰性眉题和处处入场动画列为**可能的生成式默认**，不是永远不可用的禁令。
- Vercel 原作者的 [web-design-guidelines SKILL.md](https://github.com/vercel-labs/agent-skills/blob/main/skills/web-design-guidelines/SKILL.md) 是审查工作流，具体要求来自其实时 [Web Interface Guidelines](https://github.com/vercel-labs/web-interface-guidelines/blob/main/command.md)：原生语义、焦点、输入错误、减少动态、长文本、触摸替代、性能和状态反馈。它是审查清单，不保证视觉有独特性；某些规则例如把所有 UI 状态放进 URL 不应照搬到包含房间凭证的本机应用。
- 已读取 Vercel 的 [React Best Practices SKILL.md](https://github.com/vercel-labs/agent-skills/blob/main/skills/react-best-practices/SKILL.md)：优先排除等待瀑布、无用依赖和不必要工作。本项目是原生 DOM/JS，React hooks、RSC 和 Next.js 规则不适用；可借鉴测量、避免阻塞输入和减少无谓重绘，不能据此要求迁移框架。
- 本机实际读取 **game-ui-frontend**：`plugins/cache/openai-curated/game-studio/0722921d/skills/game-ui-frontend/SKILL.md`。它针对游戏 HUD，而非视频会议：先保护游戏画面，少量必要常驻操作，低频内容按需展开，状态变化时才用动画。本文借用“保护观看画面”的原则，**不把其 HUD 面积比例当作本产品实测标准**。
- 本机实际读取 **visualize**：`plugins/cache/openai-bundled/visualize/1.0.66/skills/visualize/SKILL.md`；其与设计比较相关的建议是用少量有意义的可交互替代方案、保持状态语义一致，不制造没有证据的指标。该技能面向会话内可视化，其宿主组件和配色规范不直接约束本产品。另读取 **Sites**：`plugins/cache/openai-curated-remote/sites/1.1.2/skills/sites/SKILL.md`，它主要是网站制作与发布流程，不能作为本地产品效果的设计证据。

以上本机路径均相对于 Codex 用户目录；前两个公开技能仅在线阅读，不视作已安装。跨源准则：Apple 的[设计原则](https://developer.apple.com/design/human-interface-guidelines/design-principles/)强调清晰反馈、可恢复、上下文和用户控制；其[动效](https://developer.apple.com/design/human-interface-guidelines/motion)与[反馈](https://developer.apple.com/design/human-interface-guidelines/feedback)建议动效要有意义且简短、重要反馈与打断程度相称。

## 对现有实验室的证据与判断

1. **覆盖广，但“81”不是质量分数。** [index.html](../../demos/frontend-lab/index.html) 允许三个阶段分别选择三种结构，再选三种主题；[design-qa.md](../../demos/frontend-lab/design-qa.md) 记录源码和打包结果各 22 项 DOM/状态检查。它证明组合可运行到被检查的状态，不证明 81 套都易懂或视觉优秀。对普通体验者，开头先理解这么多组合可能比先加入朋友更费力；这是基于控制台层级的设计假设，需让新人实际尝试验证。
2. **画面优先有好的起点，仍有可检验的风险。** [edge.css](../../demos/frontend-lab/layouts/edge.css) 让观看画面铺满空间，并把操作放在边缘；这比三个等权大面板更贴合观看任务。但边缘控制压在画面上，且需检查深浅画面下的可读性、窄窗换行、全屏及键盘焦点是否被遮住；这些是待验收风险，不是已观察到的缺陷。
3. **状态模型有价值，氛围仍可更有辨识度。** [ui.js](../../demos/frontend-lab/ui.js) 对断线、共享结束和假画面明确标示，避免旧帧冒充直播；[app.js](../../demos/frontend-lab/app.js) 在停播后提示麦克风保留。可是视觉表达仍大多是文字、卡片与按钮的组合：把名字替换成任意产品后，其“朋友聚在一起，轮流把画面给大家看”的关系是否仍然成立，尚无证据。应以关系与状态转换作为造型来源，而不是加一个渐变或又换一组主题。
4. **离线素材和动效并不证明真实体验。** 演示图是静态虚构游戏场景、系统选屏是模拟；候选正式页面已观察入场、非公开建房、语音和影院主题，但不能由此推断正在变化的视频、真实声画、权限、三机或所有布局已通过。现在应比较真实视口中的关键状态和失败恢复，而不是把 DOM 通过数当成视觉验收。

## 可检验的设计与实现准则

| 目标 | 设计约束 | 验收方法 |
| --- | --- | --- |
| 第一眼有重点 | 入场只让人先看懂“哪里有朋友/如何创建或手动加入”；语音先看到谁在、自己能做什么；观看优先呈现完整画面。每个状态选择一个主视觉中心。 | 用相同视口看入场、三人语音、正在看与断线四张实际截图；让未参与设计的人在 5 秒指出位置、状态、下一步。记录误答，不给出通过结论前不声称测试结果。 |
| 非模板化 | 先画内容关系草图，明确房间、成员、画面怎样连续变换；给每道边线、标签和底色说明含义。保留必要的常规控件，不用形式差异损害学习成本。 | 做“去 logo”测试：遮住产品名后是否仍能辨认这个场景；删除任一装饰，看是否丢失真实信息。由人比较两套方案而不是统计主题数。 |
| 中文可读 | 使用适合汉字的系统字体回退、清楚的字号/行高层级；真实长房名和权限错误参与布局；避免对中文强行套用西文大字距。按浏览器断行处理标点，并核查中英数字混排。[W3C 中文排版需求](https://www.w3.org/International/clreq/)是排版参考，不是直接规定此产品字号的测试结论。 | 100% 和 200% 缩放、窄窗口、长房名、中英混排；文字完整可读、操作不溢出。对被截断的长名称提供可访问的完整名称，不只靠 hover。 |
| 即时反馈与可恢复 | 每次加入、共享、取消、停播都展示真实的等待、成功或失败；等待不能伪装成成功。声明系统声音隔离未知仍会发声，停止画面保留语音；请求结果来自真实状态。 | 模拟拒绝、取消、断线和恢复，逐项核对文案、按钮状态、焦点与真实状态；真实设备测试另列，不把模拟通过写成采集成功。 |
| 键盘、触摸、动态 | 原生 button/label，Tab 顺序和可见焦点；模态框关闭焦点回原处；任何手势有点击与键盘替代。常用控件建议至少 44×44 CSS px，作为本项目舒适目标；[WCAG 2.2 AA](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html) 的最低要求是 24×24，带例外。非必要动画遵从减少动态，[交互触发动画可关闭](https://www.w3.org/WAI/WCAG22/Understanding/animation-from-interactions.html)属 AAA。 | 仅键盘完成创建/加入、麦克风、共享、停止和离开；用触屏或触控仿真；开启减少动态重复流程，状态信息不依赖动画表达。 |
| 性能与真实视频 | 不让视觉过渡复制/重建真实 video 或重协商 WebRTC；操作响应不等动画结束。优先合成友好的 transform/opacity，但仍应通过浏览器性能工具测量，而不是认定零成本。[web.dev 动画指南](https://web.dev/articles/animations-guide)建议先检查实际渲染。 | 使用移动画面、低配设备和窗口变化，比较切换前后卡顿、长任务、掉帧以及焦点；独立记录 UI 帧率与媒体采集/发送统计，不承诺特定 FPS。 |

不应把“浅底＋陶色”“深底＋霓虹”“大字＋眉题”“满屏圆角卡片”“每项 hover 上浮”“模糊玻璃”“永远发光的在线点”当成自动加分项。它们可以是特定场景下的选择，但不能代替可理解的状态、真实素材、中文排版和任务完成证据。也不要伪造说话波形、低延迟数值、在线成员或系统声音隔离状态来制造高级感。

## 两个可实现但有明确取舍的原型

### A. 一间会展开的房间

入场是一列有真实人数和共享状态的房间门牌，点击后门牌在原位置扩成房间；成员围绕同一个共享席位，而不是把头像、状态、控制割裂成面板。朋友开始共享时，共享席位扩展为完整画面，成员缩为小型边栏；停止时收回席位，语音与当前麦克风状态不变。动效仅解释对象的连续性，用户可立即操作；不支持或减少动态时直接切换并保持同样的文字与焦点。

实现：保留一个长期存在的 video 元素，通过 CSS grid 区域或受控布局变换改变其容器；加入、席位与断线都由现有真实状态驱动，先在离线实验室验证，再对接正式服务。失败/取消回到原门牌并保留上下文。取舍：连续空间感强，但布局变化可能令焦点或屏幕阅读器迷失；必须验证 DOM 顺序、焦点和播放不中断。

### B. 共看画面边缘的“随叫随到”控制

画面按原比例完整显示；常驻只保留清晰的分享者状态与麦克风/停止等关键操作。音量、邀请、诊断等由靠边的按钮按需展开；触摸、键盘聚焦和鼠标都能显式唤出，焦点位于操作区时不自动隐藏。无共享时画面区域明确说明“还没有画面”和下一步，断线时显示可恢复状态，不留旧帧冒充直播。

实现：原生按钮和可关闭的侧面抽屉，video 层不重建；浮层有不透明或足够对比的底，滚动与焦点行为可预测。减少动态时直接显示/隐藏，切换不得打断画面。取舍：更沉浸，但控制发现性与遮挡有冲突；在动态亮暗画面、窄窗、键盘和触摸下对照有常驻控制的版本，若参与者找不到静音或停播，就增加明确常驻入口。

两种原型应以同一组真实任务、相同窗口和同一份失败场景对照；最后由用户体验和可复现证据决定，不预先宣布哪套“最优”。
