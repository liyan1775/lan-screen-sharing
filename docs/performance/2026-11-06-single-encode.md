# 2026-11-06：共享视频只编码一次

用户要求优化游戏直播性能，并明确“不要以降低质量为手段”。本候选保留原有三个画质档位，默认仍为 1920×1080、60 FPS、最高 8 Mbps，不增加游戏负载降档或自动编码器切换。

## 改动及开销来源

原来每增加一位观众，分享者浏览器就会增加一路视频和系统声音编码。本次改为浏览器只向本机 EXE 编码一次，EXE 将相同的 RTP 编码负载直接发给两位观众。转发不解码、不重新压缩，也不生成较低清晰度的版本。每位观众使用独立的 DTLS/SRTP 连接与重传缓存；语音和文字仍使用原有浏览器连接。

本机连接建立并收到接收预算后才挂入视频轨道，避免浏览器按较低的初始带宽估计启动并缩小画面。该预算仅用于同一台电脑的媒体连接；发送端仍执行所选档位的原有码率上限。转发复用每条轨道的接收缓冲区，成员加入/离开时才重建转发列表，逐包路径没有额外的自定义统计计数。

同时保留前一轮的后台本机预览暂停、隐藏界面停止无用轮询、低频诊断和重复采集/编码配置跳过。暂停的是分享者自己的播放器，采集、系统声音、麦克风和观众播放继续。参见[前一轮性能记录](2026-11-05.md)。

## 画质证据

严格浏览器用例使用原生 WebRTC、1920×1080 / 60 FPS 合成源、两位观众及三人同时开启的合成麦克风。分享端与观众使用不同浏览器进程。用例检查实际编解码报告，要求唯一视频编码器和两位观众都保持 1920×1080，5 秒计数差值的实际编解码帧率均至少 57 FPS，参数仍为 60 FPS / 8 Mbps；同时检查失焦时本机预览暂停、传输继续、重新聚焦恢复同一采集。

首次完整 11 项传输回归中的严格用例实测：分享端编码 60.16 FPS，观众解码 59.97 / 60.07 FPS，分辨率均为 1920×1080。其余用例覆盖系统声音与麦克风分离、拒绝麦克风、满员拒绝、停止共享保留语音、观众间语音、本机连接恢复及双方刷新。

Go 原生传输测试用逐包变化的负载核对两位接收端的编码内容、序号和时间戳，拒绝第三位接收端，并确认移除一位观众不会中断另一位、旧会话的迟到停止不能关闭新会话。协议和本机 API 测试检查同源本机控制凭证、消息大小、当前共享者及房间成员边界。

## CPU 对照与有效性

测量脚本为 `scripts/benchmark-encoding.mjs`。固定同一 1080p60 合成源、两位独立观众和系统声音，不开启三人麦克风。每次预热后采集 20 秒，按 A/B、B/A 交替运行两组。CPU 范围包括分享者整个浏览器的进程 CPU 时间及分享者本机 Go 程序的 CPU 时间，排除观众的解码进程；不将浏览器到 Go 的工作转移算作收益。

有效对照须同时满足每路实际 1080p、实际至少 57 FPS、参数 60 FPS / 8 Mbps。当前脚本还检查窗口前后尺寸和浏览器的清晰度调整计数，候选的观众解码帧率不得比对应基线低超过 2%。这 2% 仅用于合成采样波动，游戏 low 帧验收仍不允许默认退步。

第一轮以 `局域网屏幕共享-0.4.1-performance.exe` 为基线，候选两次均通过实际 1080p60 门槛；基线两次在采样时缩小到 1280×720，且浏览器报告 CPU 受限。故[这一轮完整原始记录](2026-11-06-single-encode.json)的整体画质门槛失败，不能用于声称“同画质 CPU 降低百分比”。保留失败样本，不通过删除样本或放宽分辨率检查取得性能结论。

随后以已暂停本机预览的双编码版作为基线，在[页面会话隔离修复前的完整 A/B、B/A 对照](2026-11-06-before-session-isolation.json)中，四个窗口均通过同画质门槛。两版均为 VP8、实际 1920×1080、60 FPS / 8 Mbps 参数；区间平均 QP 均为 2，编码分辨率调整计数不变。分享端浏览器加 Go 的平均 CPU 等效逻辑核约为 5.65 → 2.56，按 16 个逻辑处理器归一化为约 35.3% → 16.0%。约 54.8% 的差异只属于这一轮合成场景和其中记录的构建，不能承诺所有负载都有同样降幅。

最终完成页面会话隔离的内部构建也做了[两组成对复测](2026-11-06-acceptance.json)：候选两次均保持实际 1080p，观众约 59.3–59.7 FPS；旧版两次缩小为 720p，约 45–50 FPS，因此这一轮的整体 `qualityGate.passed` 为 false，同样不能用于同画质百分比结论。[另一轮尝试](2026-11-06-game-priority-comparison.json)包含一个基线媒体停止的无效窗口，也保留原样。

以上数据表明候选减少了重复编码，同时在这些受测条件下保持实际画质。代价是 Go 本体工作集从约 16–18 MiB 增至约 30 MiB；浏览器加 Go 的总常驻内存和 GPU 使用率未测，不声称这些指标同样减半。

```powershell
$env:LANSW_EXE = (Resolve-Path 'dist/局域网屏幕共享-single-encode.exe').Path

node --test tests/e2e/performance.spec.js
node --test tests/e2e/frontend-hig.spec.js
node scripts/benchmark-encoding.mjs --baseline dist/局域网屏幕共享-0.4.1-game-priority.exe --candidate dist/局域网屏幕共享-single-encode.exe --browser 'C:/Program Files (x86)/Microsoft/Edge/Application/msedge.exe' --output dist/single-encode-comparison.json --seconds 20 --pairs 2
```

运行编码对照时不同时执行其他浏览器回归、构建或 CPU 压力任务。构建在旁边生成同名 `.licenses.txt`，包含 Pion 及实际运行依赖的许可原文。早期测量用内部版本 0.4.1 的独立文件名，最终公测版为 0.5.0，三名成员须统一更新。

## 真实游戏验收

上述结果来自同机合成媒体，不是物理显示器采集或游戏帧时间。尚未取得目标游戏的基线和直播 CSV，不能据此保证游戏 1% low / 0.1% low 完全无损，也不能把浏览器进程 CPU 当成 GPU 使用率或整机功耗。

用户随后明确“验收可以不用真实游戏”，因此本轮按实际画质/帧率、分享端总 CPU 和三人功能回归验收，真实游戏记录不再作为本轮交付的前置条件。

若后续需要补充游戏数据，可使用已有的 `scripts/capture-game-frametimes.ps1` / `scripts/compare-game-frametimes.mjs`：同一游戏版本、固定场景和设置下交替采集至少三组“只运行游戏”与“游戏 + 两位观众”，观众使用另外两台设备。比较保留长卡顿，核对 1% low、0.1% low、P99 和 P99.9，默认退步容差为 0。操作、定义和数据拒绝条件见[真实游戏采集说明](2026-11-05.md#真实游戏-low-帧验收仍未完成)。
